## 단일 모델 알람의 한계

YOLO는 빠르게 객체 후보를 찾는 데 강합니다. 하지만 화재, 쓰러짐, 위험 행동처럼 맥락이 필요한 이벤트는 박스 하나만으로 판단하기 어렵습니다.

CLIP이나 VLM은 장면의 의미를 보조적으로 확인하는 데 사용할 수 있습니다. 탐지 모델이 후보를 만들고, 멀티모달 모델이 상황을 한 번 더 확인하는 구조가 hybrid alarm logic입니다.

## 결합 방식

| 방식 | 설명 |
| --- | --- |
| AND 조건 | 두 모델이 모두 동의할 때 알람 |
| OR 조건 | 하나라도 감지하면 알람 |
| 단계형 | YOLO 후보를 VLM이 재판단 |
| 가중 점수 | 모델별 confidence를 합산 |

## 오탐과 미탐의 균형

AND 조건은 오탐을 줄이는 데 유리하지만 미탐이 늘 수 있습니다. OR 조건은 민감하지만 알람이 많아질 수 있습니다. 이벤트의 위험도에 따라 조건을 다르게 잡아야 합니다.

화재처럼 놓치면 안 되는 이벤트는 민감도를 높이고, 반복 오탐이 많은 이벤트는 재확인 단계를 추가하는 식입니다.

## 운영 로그

알람이 발생했을 때 YOLO 결과, CLIP score, 최종 조건, threshold를 함께 저장해야 합니다. 그래야 오탐 분석 시 어떤 단계가 문제였는지 알 수 있습니다.

## 후보 생성과 재판단 분리

Hybrid 구조에서 YOLO는 빠른 후보 생성기 역할을 맡기 좋습니다. 모든 프레임을 VLM이나 CLIP에 넣으면 비용이 커지기 때문에, 먼저 YOLO가 사람, 연기, 불꽃, 차량 같은 후보를 찾고 후보 영역만 재판단하는 방식이 현실적입니다.

이때 crop 영역을 너무 타이트하게 잡으면 맥락이 사라질 수 있습니다. 예를 들어 쓰러짐 판단은 사람 박스뿐 아니라 주변 바닥, 자세, 움직임 흐름이 중요합니다. 후보 crop에는 약간의 margin을 두는 것이 좋습니다.

## 알람 상태 머신

알람은 단발성 메시지가 아니라 상태를 가집니다. 후보 감지, 재확인, 알람 발생, 사용자 확인, 종료 같은 흐름으로 관리하면 중복 알람을 줄일 수 있습니다.

| 상태 | 설명 |
| --- | --- |
| candidate | YOLO가 후보를 감지 |
| verifying | CLIP/VLM으로 재확인 |
| active | 알람 발생 |
| acknowledged | 사용자가 확인 |
| closed | 상황 종료 |

## 운영 튜닝

처음에는 오탐을 줄이려고 조건을 강하게 걸기 쉽습니다. 하지만 안전 이벤트에서는 미탐 비용이 더 클 수 있습니다. 이벤트 종류별로 목표를 다르게 두고, 위험도가 높은 이벤트는 보수적으로 알람을 발생시키는 것이 좋습니다.

중요한 것은 알람을 발생시킨 근거를 남기는 것입니다. 그래야 나중에 "왜 울렸는가"와 "왜 안 울렸는가"를 같은 기준으로 분석할 수 있습니다.
