## 왜 Local LLM인가

사내망이나 폐쇄망에서는 외부 API 호출이 어렵습니다. 법령 문서, 작업 매뉴얼, 내부 규칙처럼 민감한 데이터가 있는 경우에도 로컬 LLM 운영을 검토하게 됩니다.

Local LLM은 보안과 통제 면에서 장점이 있지만, 모델 선택과 운영 비용을 직접 책임져야 합니다.

## 후보 모델을 볼 때

| 기준 | 설명 |
| --- | --- |
| 모델 크기 | 운영 GPU 메모리에 맞는가 |
| 한국어 성능 | 실제 질문에서 답변 품질이 충분한가 |
| 추론 속도 | 동시 요청을 감당할 수 있는가 |
| 라이선스 | 사내 서비스 사용에 문제가 없는가 |
| RAG 적합성 | 검색 근거를 잘 반영하는가 |

## Qwen과 Gemma 같은 경량 모델

경량 모델은 큰 모델보다 빠르고 운영이 쉽지만, 복잡한 추론이나 긴 문맥에서 한계가 있을 수 있습니다. 그래서 모델 자체 성능만 보지 말고 RAG 품질, 프롬프트 구조, reranker 사용 여부를 함께 봐야 합니다.

법령 판단처럼 근거가 중요한 작업에서는 모델이 문서를 기억하는 능력보다 검색된 근거를 충실히 따르는 능력이 더 중요합니다.

## 운영 방식

로컬 LLM 서버는 모델 로딩 시간, GPU 메모리, 큐 대기 시간, 토큰 생성 속도를 모니터링해야 합니다. 사용량이 많아지면 모델 복제, 요청 제한, 캐싱 전략이 필요합니다.

## RAG와 함께 쓸 때의 기준

사내망에서 Local LLM을 쓰는 경우 대부분 내부 문서 검색과 함께 붙습니다. 이때 모델이 모든 지식을 외우는 것보다 검색된 문서를 충실히 따르는지가 더 중요합니다. 작은 모델이라도 RAG 프롬프트가 안정적이면 업무용 질의응답에는 충분할 수 있습니다.

테스트 질문은 단순 요약, 특정 조항 찾기, 예외 조건 판단, 모호한 질문 거절로 나눠 구성하는 것이 좋습니다. 특히 근거가 없는 질문에 그럴듯한 답을 만드는지 확인해야 합니다.

## 운영 비용의 종류

로컬 모델은 API 비용이 없다고 생각하기 쉽지만 실제로는 다른 비용이 생깁니다. GPU 장비, 전력, 장애 대응, 모델 업데이트, 보안 패치, 로그 관리가 모두 운영 비용입니다.

| 비용 | 확인 포인트 |
| --- | --- |
| 장비 | 필요한 VRAM과 동시 요청 수 |
| 유지보수 | 모델 교체와 서버 패치 |
| 품질 관리 | 평가셋과 회귀 테스트 |
| 보안 | 접근 제어와 로그 정책 |

## 답변 품질 관리

Local LLM은 한 번 띄우고 끝나는 시스템이 아닙니다. 문서가 바뀌거나 사용자 질문 패턴이 바뀌면 품질도 달라집니다. 자주 들어오는 질문, 실패한 질문, 근거가 부족한 질문을 모아 평가셋으로 만들어야 합니다.

이 평가셋으로 모델 교체나 프롬프트 변경 전후를 비교하면 감으로 운영하는 일을 줄일 수 있습니다.
