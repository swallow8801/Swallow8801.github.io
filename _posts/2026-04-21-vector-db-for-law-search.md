## 법령 검색은 chunk가 중요하다

RAG에서 검색 품질은 LLM 답변 품질을 크게 좌우합니다. 법령 문서는 조항 단위가 의미 단위이기 때문에 일반 문서처럼 글자 수 기준으로 자르면 근거가 깨질 수 있습니다.

가능하면 조, 항, 호, 별표 단위를 보존하고, 답변에 표시할 수 있는 조항 번호를 metadata로 남겨야 합니다.

## Metadata 설계

| 필드 | 용도 |
| --- | --- |
| law_name | 법령명 필터 |
| article_no | 조항 번호 표시 |
| effective_date | 시행일 기준 검색 |
| hierarchy | 조, 항, 호 구조 |
| source_url | 원문 링크 |
| keywords | 키워드 보조 검색 |

## 검색 흐름

기본 검색은 embedding similarity로 시작합니다. 그 다음 metadata filter로 법령 범위나 시행일을 제한하고, reranker로 상위 후보를 다시 정렬할 수 있습니다.

질문이 짧거나 용어가 명확한 경우에는 키워드 검색이 더 잘 맞을 때도 있습니다. 그래서 vector search와 keyword search를 함께 쓰는 hybrid search를 고려할 만합니다.

## 답변 근거 표시

검색 결과는 LLM에 넣는 것으로 끝내지 말고 사용자에게도 보여줘야 합니다. 어떤 조항을 근거로 판단했는지 표시하면 답변 신뢰도를 높일 수 있고, 오류가 났을 때 디버깅도 쉬워집니다.

## Chunk 크기 실험

법령 검색에서 chunk가 너무 작으면 문맥이 부족하고, 너무 크면 검색 결과가 뭉뚱그려집니다. 조항 단위로 자르되, 항과 호가 독립적으로 의미를 가질 때는 더 작은 단위로 나눌 수 있습니다.

실험할 때는 같은 질문셋으로 top-k 검색 결과를 비교합니다. 정답 조항이 top-3 안에 들어오는지, 불필요한 조항이 반복적으로 섞이는지, 시행일이 다른 문서가 잡히는지 확인합니다.

## Hybrid Search가 필요한 이유

법령에는 정확한 용어가 중요합니다. 사용자가 조항 번호나 특정 법령명을 입력한 경우에는 벡터 검색보다 키워드 검색이 더 정확할 수 있습니다. 반대로 사용자가 자연어로 상황을 설명하면 벡터 검색이 유리합니다.

그래서 실제 시스템에서는 keyword score와 vector score를 함께 계산하고, 필요하면 reranker로 최종 순서를 조정합니다. 이 구조는 초기 구현은 조금 복잡하지만 검색 실패를 줄이는 데 도움이 됩니다.

## 변경 이력 관리

법령은 시간이 지나며 바뀝니다. 같은 질문도 기준 날짜에 따라 답이 달라질 수 있습니다. Vector DB에는 시행일, 개정일, 폐지 여부 같은 metadata를 반드시 남겨야 합니다.

답변에도 기준 날짜를 표시하면 사용자가 판단 범위를 이해하기 쉽습니다. 검색 시스템이 최신 조항만 보는지, 과거 조항도 함께 보는지는 서비스 목적에 맞춰 명확히 정해야 합니다.
