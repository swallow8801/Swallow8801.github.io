## 실시간 알림의 흐름

AI 관제 시스템에서 이벤트는 모델 worker에서 발생하지만, 사용자는 웹 대시보드에서 확인합니다. 이 사이에는 이벤트 저장, 알림 전송, 수신 확인, 상태 변경이 이어집니다.

Socket.IO는 웹 클라이언트와 서버 사이의 실시간 통신을 구현할 때 사용할 수 있는 선택지입니다.

## 기본 구조

| 단계 | 역할 |
| --- | --- |
| AI Worker | 이벤트 생성 |
| API Server | 이벤트 저장 |
| Socket Server | 연결된 클라이언트에 브로드캐스트 |
| Dashboard | 알림 표시와 확인 처리 |
| Database | 이벤트 상태 저장 |

## 이벤트 중복 처리

같은 상황에서 알람이 계속 발생하면 사용자는 피로해집니다. 이벤트 deduplication, cooldown, 상태 기반 업데이트가 필요합니다.

예를 들어 같은 카메라에서 같은 ROI의 화재 후보가 5초 안에 반복되면 새 알람을 만들기보다 기존 알람의 confidence와 마지막 감지 시간을 갱신할 수 있습니다.

## 신뢰성

실시간 메시지는 빠르지만, 저장을 대체하면 안 됩니다. 알림은 놓칠 수 있으므로 이벤트는 먼저 DB에 저장하고, Socket.IO는 사용자에게 빠르게 알려주는 채널로 보는 것이 안전합니다.

## Room 설계

관제 시스템에서는 모든 사용자에게 모든 이벤트를 보낼 필요가 없습니다. 담당 구역, 권한, 카메라 그룹에 따라 받을 알림이 달라질 수 있습니다. Socket.IO의 room을 이용하면 구역별 브로드캐스트를 구성할 수 있습니다.

예를 들어 `site:seoul`, `camera:12`, `role:admin` 같은 room을 두면 이벤트 종류에 따라 알맞은 사용자에게만 전달할 수 있습니다. 같은 알람이라도 관리자는 전체 정보를 보고, 현장 담당자는 본인 구역의 이벤트만 받게 만들 수 있습니다.

## 재연결과 누락 보정

웹소켓 연결은 끊길 수 있습니다. 사용자가 네트워크를 이동하거나 브라우저가 잠시 멈추면 실시간 메시지를 놓칠 수 있습니다. 그래서 클라이언트가 재연결될 때 마지막으로 받은 이벤트 ID 이후의 이벤트를 REST API로 다시 조회하는 흐름이 필요합니다.

이 구조를 넣으면 Socket.IO는 빠른 알림 채널로 쓰고, DB는 최종 상태의 기준으로 유지할 수 있습니다. 실시간 시스템일수록 "빠른 표시"와 "정확한 기록"을 분리하는 것이 중요합니다.

## 이벤트 스키마

실시간 이벤트는 스키마가 안정적이어야 합니다. 프론트엔드가 매번 다른 구조의 메시지를 받으면 UI 처리가 어려워집니다.

```json
{
  "event_id": "evt_001",
  "camera_id": "cam_12",
  "type": "fire",
  "severity": "critical",
  "status": "active",
  "created_at": "2026-05-12T10:00:00+09:00"
}
```

이벤트 ID와 상태를 명확히 두면 중복 표시, 상태 갱신, 사용자 확인 처리가 쉬워집니다.
