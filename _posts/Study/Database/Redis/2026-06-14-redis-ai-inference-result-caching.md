## 들어가며

추론 서버를 운영하다 보면 "방금 전에 본 것과 똑같은 입력"이 생각보다 자주 들어옵니다. 같은 문서를 다시 분석 요청하거나, VLM·LLM에 동일한 프롬프트가 반복되거나, 동일 이미지에 대한 재조회가 들어오는 식입니다. 이때마다 GPU를 다시 돌리는 것은 같은 계산을 두 번 하는 낭비입니다.

Redis는 이 낭비를 줄이는 가장 단순한 도구입니다. "입력 → 결과"를 메모리에 저장해 두고, 같은 입력이 다시 오면 GPU 대신 메모리에서 즉시 돌려줍니다. 이 글은 추론 결과 캐싱의 키 설계, TTL, 무효화, 그리고 **캐싱하면 안 되는 경우**까지 정리합니다.

---

## 캐싱이 통하는 입력, 통하지 않는 입력

캐싱은 만능이 아닙니다. 효과는 입력의 성격에 달려 있습니다.

- **잘 맞는 경우**: 동일 입력이 반복되고(같은 문서·프롬프트·이미지), 같은 입력이면 결과가 변하지 않는(결정적) 추론. 예) 고정 모델로 같은 이미지를 분류, 같은 질의에 대한 RAG 검색·답변.
- **안 맞는 경우**: 입력이 매번 미세하게 다른(실시간 CCTV 프레임처럼 사실상 매번 새 입력) 작업, 또는 같은 입력이라도 시점에 따라 결과가 달라져야 하는 작업.

핵심 질문은 "같은 입력이 반복되는가"와 "같은 입력이면 같은 답이어도 되는가" 둘입니다. 둘 다 '예'일 때만 캐싱이 의미가 있습니다. 실시간 영상 프레임처럼 매 프레임이 다른 입력이면 캐시 적중률이 0에 가까워 오히려 오버헤드만 늘어납니다.

---

## 키 설계: 입력을 무엇으로 식별할까

캐시의 정확성은 키 설계에서 갈립니다. "같은 입력"을 무엇으로 판단할지를 키에 빠짐없이 담아야 합니다. 입력 내용만으로 키를 만들고 모델 버전을 빼먹으면, 모델을 교체한 뒤에도 옛 결과가 반환되는 위험한 버그가 생깁니다.

키에는 보통 다음을 모두 포함합니다.

- **입력 내용의 해시** — 이미지·문서·프롬프트 등 원본을 그대로 키에 넣지 말고 해시로 압축
- **모델 식별자·버전** — 모델이 바뀌면 같은 입력이라도 다른 답이어야 함
- **전처리/파라미터** — 임계값, 해상도 등 결과에 영향을 주는 설정

```python
import hashlib, json, redis

r = redis.Redis(host="localhost", port=6379, db=0)

def cache_key(image_bytes: bytes, model_ver: str, params: dict) -> str:
    h = hashlib.sha256(image_bytes).hexdigest()[:16]
    p = hashlib.sha256(json.dumps(params, sort_keys=True).encode()).hexdigest()[:8]
    return f"infer:{model_ver}:{h}:{p}"

def infer_with_cache(image_bytes, model_ver, params, run_model):
    key = cache_key(image_bytes, model_ver, params)
    cached = r.get(key)
    if cached is not None:
        return json.loads(cached)          # 캐시 적중: GPU 건너뜀
    result = run_model(image_bytes, params)  # 캐시 미스: 실제 추론
    r.set(key, json.dumps(result), ex=3600)  # TTL 1시간
    return result
```

`params`를 `sort_keys=True`로 직렬화하는 이유는, 같은 설정인데 키 순서만 달라 다른 해시가 나오는 일을 막기 위해서입니다. 작은 부주의가 적중률을 갉아먹습니다.

## TTL: 캐시를 얼마나 오래 들고 있을까

TTL(Time To Live)은 캐시 항목의 수명입니다. `ex=3600`이면 1시간 뒤 자동 삭제됩니다. TTL은 두 가지를 동시에 조율합니다.

- **너무 길면**: 메모리가 계속 차오르고, 모델·기준이 바뀌었는데도 옛 결과가 오래 남습니다.
- **너무 짧으면**: 같은 입력이 다시 오기 전에 만료돼 적중률이 떨어집니다.

정답은 "결과가 얼마 동안 유효한가"에 달려 있습니다. 고정 모델의 결정적 추론은 길게 잡아도 되지만, 외부 데이터(예: 법령·문서)가 갱신될 수 있는 RAG 결과는 그 갱신 주기보다 짧게 잡아야 합니다. 메모리가 한정적이면 Redis의 `maxmemory`와 `allkeys-lru` 같은 축출(eviction) 정책으로, 오래 안 쓰인 항목부터 자동으로 밀어내게 설정할 수 있습니다(`<측정값>` — 적정 TTL과 메모리 한도는 실제 트래픽·적중률을 보고 조정).

---

## 무효화: 모델이 바뀌면 캐시는 어떻게 되나

캐시에서 가장 까다로운 주제가 무효화입니다. 다행히 키에 모델 버전을 넣어 뒀다면, 모델 교체 시 무효화는 저절로 해결됩니다. **새 버전 문자열이 키 앞에 붙으므로 옛 캐시는 자연히 조회되지 않고, TTL이 지나면 알아서 사라집니다.** 별도로 옛 키를 일괄 삭제하지 않아도 됩니다.

즉시 비워야 한다면 패턴 삭제도 가능하지만, 운영 중인 Redis에서 `KEYS`로 전체를 훑는 것은 부하가 크므로 `SCAN`으로 나눠 지우는 편이 안전합니다.

```python
def invalidate_model(model_ver: str):
    for key in r.scan_iter(match=f"infer:{model_ver}:*", count=500):
        r.delete(key)
```

가능하면 "버전을 키에 포함 → 자연 만료"에 기대고, 명시적 삭제는 정말 필요할 때만 쓰는 것을 권합니다.

## 적중률을 측정하지 않으면 캐시는 추측일 뿐

캐시를 넣었다면 효과를 숫자로 봐야 합니다. 적중률이 낮으면 캐시는 메모리만 먹는 장식이 됩니다.

- **적중률(hit rate)**: 전체 요청 중 캐시로 처리된 비율 (`<측정값>`)
- **지연 비교**: 캐시 적중 시 vs. 실제 추론 시 응답 시간 (`<측정값>`)
- **GPU 부하 변화**: 캐싱 적용 전후 GPU 사용률·처리 요청 수 (`<측정값>`)
- **메모리 사용량**: Redis가 점유하는 메모리와 축출 발생 빈도 (`<측정값>`)

> 확인 필요: 위 수치는 입력 반복 패턴에 전적으로 좌우됩니다. 적중률이 낮게 측정되면 캐싱 자체를 재검토해야 하며(앞의 "통하지 않는 입력"에 해당할 수 있음), 무작정 TTL만 늘리는 것은 답이 아닙니다.

## 정리

추론 결과 캐싱은 "같은 입력에 두 번 GPU를 쓰지 않는다"는 단순한 아이디어지만, 제대로 쓰려면 세 가지를 챙겨야 합니다. 입력을 빠짐없이 식별하는 **키 설계**(특히 모델 버전 포함), 결과 유효 기간에 맞춘 **TTL**, 그리고 모델 버전을 키에 녹여 **무효화를 자연 만료에 맡기는** 구조입니다.

무엇보다 캐싱을 적용하기 전에 "이 서비스의 입력이 정말 반복되는가"를 먼저 확인하고, 적용한 뒤에는 적중률을 측정해 효과를 검증해야 합니다. 반복되지 않는 입력에 건 캐시는 이득 없이 복잡도만 더합니다.
