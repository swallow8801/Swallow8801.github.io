## 들어가며

GPU 추론 서버를 운영하다 보면 `nvidia-smi`를 정말 자주 들여다보게 됩니다. "지금 GPU가 잘 돌고 있나?", "메모리는 얼마나 남았지?", "이 프로세스가 GPU를 잡고 있는 게 맞나?" — 답은 대부분 이 한 줄짜리 명령으로 시작합니다.

문제는 출력에 찍힌 숫자를 곧이곧대로 읽으면 종종 엉뚱한 결론에 도달한다는 점입니다. "GPU-Util 90%"가 꼭 "잘 쓰고 있다"는 뜻은 아니고, "메모리 사용량이 안 줄어든다"가 꼭 "누수"를 뜻하지도 않습니다. 이 글은 `nvidia-smi` 출력을 어떻게 읽고, 추론 서버를 운영하면서 자주 만나는 오해와 함정이 무엇인지 정리합니다.

---

## 출력에서 어디를 먼저 봐야 할까

`nvidia-smi`를 그냥 실행하면 이런 형태의 표가 나옵니다(아래 값은 형식을 보여주기 위한 예시입니다).

```
+-----------------------------------------------------------------------------+
| NVIDIA-SMI 535.129    Driver Version: 535.129    CUDA Version: 12.2         |
|-------------------------------+----------------------+----------------------+
| GPU  Name        Persistence-M| Bus-Id        Disp.A | Volatile Uncorr. ECC |
| Fan  Temp  Perf  Pwr:Usage/Cap|         Memory-Usage | GPU-Util  Compute M. |
|===============================+======================+======================|
|   0  NVIDIA A100        Off   | 00000000:01:00.0 Off |                    0 |
| 45%   62C   P0    210W / 300W |  18432MiB / 40960MiB |     97%      Default |
+-------------------------------+----------------------+----------------------+

+-----------------------------------------------------------------------------+
| Processes:                                                                  |
|  GPU   GI   CI        PID   Type   Process name              GPU Memory     |
|=============================================================================|
|    0   N/A  N/A     18213      C   python inference_server.py    17984MiB   |
+-----------------------------------------------------------------------------+
```

처음 보면 정보량에 압도되기 쉽지만, 추론 서버를 운영하는 입장에서 매일 확인할 값은 사실 몇 개로 좁혀집니다. **GPU-Util, Memory-Usage, Temp/Power, 그리고 Processes 목록**입니다. 나머지(Fan, Persistence Mode, ECC 등)는 평소엔 조용히 있다가 이상이 생겼을 때 원인을 좁히는 보조 정보 정도로 두면 충분합니다.

---

## 자주 오해하는 지표 두 가지

### "GPU-Util 97%"가 말해주는 것

`Volatile GPU-Util`은 "최근 샘플링 구간 동안 GPU에서 커널이 한 번이라도 실행되고 있던 시간의 비율"에 가깝습니다. **연산을 얼마나 꽉 채워 썼는가**가 아니라 **얼마나 자주 뭔가는 돌고 있었는가**를 보여주는 값입니다.

그래서 작은 배치를 쉴 새 없이 돌리는 추론 서버는 GPU-Util이 90% 이상으로 찍히면서도 실제 처리량(throughput)은 기대보다 낮을 수 있습니다. 커널은 자주 실행되지만 매번 짧고, 그 사이사이 실행 준비·데이터 전송 같은 오버헤드가 끼어들기 때문입니다. 반대로 배치를 키워 한 번에 묵직하게 처리하면 GPU-Util 수치 자체는 비슷해 보여도 실제 처리량은 더 높을 수 있습니다. **GPU-Util만으로 "잘 쓰고 있다/못 쓰고 있다"를 판단하지 말고, 처리량·지연(latency) 지표와 함께 보는 습관**이 필요합니다.

### "Memory-Usage가 안 줄어든다"가 곧 누수는 아니다

`Memory-Usage`는 프로세스가 **할당해 둔** 메모리 총량이지, 모델이 추론 한 번에 **필요로 하는** 양이 아닙니다. PyTorch 같은 프레임워크는 CUDA 메모리를 반환했다가 다시 할당받는 비용을 줄이려고 캐싱 알로케이터를 두고, 한 번 확보한 메모리를 내부적으로 재사용합니다. 그래서 추론을 마친 뒤에도 `nvidia-smi`에는 메모리가 그대로 잡혀 있는 것처럼 보입니다.

이것 자체는 정상 동작이라 수치가 안 줄어든다고 바로 누수로 단정하면 엉뚱한 곳을 파게 됩니다. 오히려 시간이 지날수록 **상한선 자체가 계속 올라가는지**(요청을 처리할 때마다 조금씩 더 많은 메모리를 붙잡는지)를 추적하는 쪽이 누수를 가려내는 더 정확한 신호입니다.

## 지표별로 정리하면

| 지표 | 실제로 보여주는 것 | 오해하기 쉬운 점 |
| --- | --- | --- |
| GPU-Util | 샘플링 구간 동안 커널이 실행되고 있던 시간 비율 | "연산을 꽉 채워 썼는가"가 아니라 "자주 뭔가 돌았는가"에 가까움 |
| Memory-Usage | 프로세스가 할당해 둔 메모리 총량 | 프레임워크의 캐싱 재사용분도 포함 → 실제 "필요량"과는 다를 수 있음 |
| Temp / Power | 현재 온도·전력 소비 | 한계치에 가까워지면 스로틀링으로 이어지는 선행 신호 |
| Processes | GPU를 점유 중인 프로세스와 각각의 메모리 사용량 | 여러 프로세스가 한 GPU를 나눠 쓸 때 충돌 원인을 좁히는 출발점 |

---

## 추론 서버에서 자주 만나는 함정

- **"Util이 높으니 충분히 쓰고 있다"는 착각**: 앞서 본 것처럼 GPU-Util은 가동 시간의 비율일 뿐 처리량을 보장하지 않습니다. 배치 크기·동시 요청 수를 바꿔 가며 처리량이 실제로 달라지는지를 함께 확인해야 진짜 그림이 보입니다.
- **"메모리가 그대로니 새고 있다"는 성급한 결론**: 캐싱 알로케이터의 정상 동작과 진짜 누수를 구분하려면 단발성 수치보다 **추세**(요청을 반복할수록 상한이 올라가는가)를 봐야 합니다.
- **여러 프로세스가 한 GPU를 공유할 때의 혼선**: `Processes` 영역은 "누가 메모리를 얼마나 잡고 있는지"는 보여주지만, "그 프로세스가 지금 이 순간 연산을 얼마나 쓰고 있는지"까지 세밀하게 보여주지는 않습니다. 같은 GPU에서 여러 서비스를 돌릴 계획이라면 이 한계를 미리 알아 두는 편이 좋습니다.
- **순간 값만 보고 판단하기**: `nvidia-smi`를 한 번 실행해서 보는 값은 그 순간의 스냅샷입니다. 부하가 출렁이는 추론 서버에서는 한 번의 스냅샷보다 **일정 주기로 모은 시계열**이 훨씬 신뢰할 수 있는 근거가 됩니다.

## 모니터링 루틴으로 끼워 넣기

당장 상태를 눈으로 보고 싶다면 `watch`로 충분합니다.

```bash
watch -n 1 nvidia-smi
```

다만 이 방식은 "지금 보고 있을 때만" 알 수 있다는 한계가 있습니다. 운영 중인 서버라면 값을 주기적으로 뽑아 로그·메트릭 파이프라인으로 흘려보내는 편이 낫습니다. `--query-gpu`와 `--format=csv` 조합을 쓰면 파싱하기 쉬운 형태로 필요한 값만 뽑을 수 있습니다.

```bash
nvidia-smi --query-gpu=timestamp,utilization.gpu,memory.used,memory.total,temperature.gpu,power.draw \
  --format=csv,noheader,nounits -l 1
```

```
2026-06-06 09:12:01, 97, 18432, 40960, 62, 210.32
2026-06-06 09:12:02, 95, 18432, 40960, 62, 208.91
2026-06-06 09:12:03, 96, 18496, 40960, 63, 211.05
```

(위 출력 역시 형식을 보여주기 위한 예시이며, 실제 값은 모델·하드웨어·부하 패턴에 따라 달라집니다.)

이렇게 모은 시계열을 메트릭 시스템(Prometheus 등)으로 흘려보내면 "GPU-Util이 갑자기 0%로 떨어진 구간"이나 "메모리 상한이 며칠에 걸쳐 조금씩 올라가는 패턴" 같은 걸 그래프로 바로 확인할 수 있습니다. 더 세밀한 프로세스별 가동률까지 보고 싶다면 NVIDIA가 제공하는 DCGM 기반 익스포터처럼 `nvidia-smi`보다 더 깊은 곳까지 보는 도구로 넘어가는 것도 검토할 만합니다.

알림 임계치(온도·메모리 사용률 등)는 GPU 모델·운영 환경마다 다르므로 직접 관찰한 값을 기준으로 잡아야 합니다(`<측정값>` — 운영 환경에서 일정 기간 수집한 뒤 정상 범위를 정해 채워 넣으세요).

## 정리

`nvidia-smi`는 GPU 상태를 들여다보는 가장 빠른 출발점이지만, 출력된 숫자를 액면 그대로 읽으면 오해하기 쉽습니다. GPU-Util은 "얼마나 자주 돌았는가"이지 "얼마나 알차게 썼는가"가 아니고, Memory-Usage는 "할당해 둔 양"이지 "당장 필요한 양"이 아닙니다. 순간 값 하나로 판단하기보다 처리량·지연과 함께, 그리고 한 번의 스냅샷이 아니라 시계열로 누적해 보는 습관을 들이면 운영 중 마주치는 혼란의 상당 부분을 줄일 수 있습니다.
