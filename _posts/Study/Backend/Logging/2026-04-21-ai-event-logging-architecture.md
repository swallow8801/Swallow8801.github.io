## 들어가며

AI 추론·관제 시스템에서 로그는 두 가지 다른 목적을 동시에 떠안습니다. 하나는 **운영 관찰**(지금 시스템이 정상인지, 얼마나 느린지)이고, 다른 하나는 **모델 개선**(어떤 입력에서 오탐·미탐이 났는지)입니다. 이 둘을 같은 로그에 섞어 두면 나중에 둘 다 제대로 쓰기 어려워집니다.

이 글에서는 AI 이벤트 로그에 무엇을 남길지, 운영용과 학습 개선용을 어떻게 분리할지, 보관 정책은 어떻게 잡을지를 정리합니다.

---

## 무엇을 남길까

추론 한 건마다 최소한 다음을 구조적(JSON)으로 남기면 나중에 질의·집계가 쉽습니다.

| 필드 | 설명 |
| --- | --- |
| `ts` | 이벤트 시각 (UTC, ISO8601) |
| `model_version` | 모델·가중치 버전 |
| `threshold` | 판정에 쓴 임계값 |
| `result` | 판정 결과 (정상/불량/클래스) |
| `score` | 신뢰도 점수 |
| `latency_ms` | 추론 소요 시간 |
| `source` | 카메라/라인 ID 등 입력 출처 |
| `input_ref` | 입력 메타(해상도, 프레임 번호) 또는 샘플 저장 경로 |

문자열 한 줄로 적기보다 구조적 로그로 남겨야 "특정 라인에서 score 0.4~0.6 구간 이벤트만" 같은 조회가 가능합니다.

---

## 운영 로그 vs 학습 개선용 로그

두 로그는 수명도, 저장소도 다릅니다.

- **운영 로그**: 헬스/지연/에러 중심. 보존 기간이 짧아도 되고, 메트릭(`/metrics`)·알림과 연결됩니다.
- **학습 개선용 로그**: 오탐·미탐 분석과 재학습 데이터 확보가 목적. 입력 메타·샘플 이미지와 함께, 더 길게 보관합니다.

처음부터 둘을 분리해 두면 나중에 데이터셋을 다시 만들 때 운영 노이즈를 걷어내는 수고를 덜 수 있습니다.

---

## 저장과 보관 정책

- **구조적 로그**: JSON 라인으로 적재하고 수집기(예: 파일 → 수집 파이프라인)로 모읍니다.
- **회전·보존**: 용량이 빠르게 늘므로 일자별 회전과 보존 기간(`<측정값>`일)을 정합니다.
- **원본 이미지**: 전부 저장할 필요는 없습니다. 경계 구간(score가 임계값 근처) 위주로 **샘플링 저장**하는 정책이 비용 대비 효율이 좋습니다.

```python
if abs(score - threshold) < SAMPLING_BAND:
    save_sample(image, meta)   # 애매한 케이스만 보관
```

## 민감정보 주의

CCTV·사람이 찍히는 입력이라면 로그·샘플에 개인정보가 섞입니다. 얼굴 등은 비식별화(블러/모자이크) 후 저장하거나, 접근 권한을 분리해 보관 범위를 최소화합니다. 보존 기간이 지난 샘플은 자동 삭제되도록 정책을 코드로 박아두는 편이 안전합니다.

---

## 정리

이벤트 로그는 "운영을 보는 눈"과 "모델을 고치는 재료"를 동시에 만듭니다. 구조적 필드로 남기고, 운영용/학습용을 분리하고, 원본은 샘플링·비식별화로 관리하는 것이 출발점입니다. 보존 기간·샘플링 비율 같은 수치는 운영하며 측정해 채워 넣으세요.
