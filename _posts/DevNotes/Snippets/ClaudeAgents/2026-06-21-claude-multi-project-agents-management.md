---

## git으로 버전 관리하기

프로젝트 레벨 에이전트(`.claude/agents/`)는 **그냥 커밋한다.** 코드처럼 PR로 리뷰하고 히스토리를 남긴다.

```bash
git add .claude/agents/ .claude/skills/
git commit -m "chore(agents): post-validator 검사 항목에 pinned 중복 추가"
```

이렇게 하면 따라오는 게 많다.

- **팀 공유.** 클론하면 모두가 같은 에이전트 세트를 쓴다. "내 Claude는 컨벤션을 아는데 네 건 모른다"가 사라진다.
- **변경 추적.** 에이전트가 어느 시점부터 이상하게 동작하면 `git log .claude/agents/`로 언제 무엇을 바꿨는지 본다. 프롬프트 한 줄 차이로 위임이 달라지므로 이 히스토리가 디버깅의 출발점이 된다.
- **리뷰 게이트.** description·tools 변경을 PR로 받으면, 권한을 무심코 넓히는 변경(`tools`에 `Bash` 슬쩍 추가 등)을 사람이 한 번 거른다.

`.gitignore`에서 `.claude/`를 통째로 무시하지 않도록 주의한다. 보통 `settings.local.json`만 무시하고 `agents/`·`skills/`·`settings.json`은 커밋한다.

## 유저 레벨 vs 프로젝트 레벨, 우선순위

여러 프로젝트를 동시에 굴릴 때 핵심은 **레벨 분리**다.

| | 위치 | 적용 범위 | git |
|---|---|---|---|
| 유저 레벨 | `~/.claude/agents/` | 내 모든 프로젝트 | 개인(별도 dotfiles repo로 관리 가능) |
| 프로젝트 레벨 | `<repo>/.claude/agents/` | 그 저장소 | 저장소에 커밋, 팀 공유 |

이름이 겹치면 **프로젝트 레벨이 이긴다.** 이 규칙을 적극적으로 쓴다.

- 어디서나 통하는 범용 역할(`git-helper`, `code-reviewer`, `docs-writer`)은 **유저 레벨**에 둔다. 새 프로젝트를 열어도 바로 있다.
- 프로젝트 특화 규칙이 필요하면, **같은 이름**의 에이전트를 그 저장소 `.claude/agents/`에 만든다. 그 프로젝트 안에서만 특화 버전이 범용 버전을 덮어쓴다.

예: 유저 레벨에 일반 `frontend-engineer`(React 기준)를 두고, 이 블로그 저장소에는 Jekyll·SCSS·디자인 토큰을 아는 `frontend-engineer`를 프로젝트 레벨에 둔다. 블로그 작업 중엔 후자가, 다른 React 앱에선 전자가 자동으로 뜬다.

## 여러 프로젝트에서 동기화 유지

같은 역할의 에이전트가 여러 저장소에 흩어지면, 시간이 지나며 서로 달라진다. 두 가지로 관리한다.

- **공통 골격은 유저 레벨에 하나만.** 프로젝트마다 복붙하지 말고, 범용 부분은 유저 레벨에 두고 프로젝트엔 차이점만 둔다. 복붙본이 많을수록 한 곳을 고쳐도 나머지가 안 따라온다.
- **프로젝트별로 갈리는 건 "사실"뿐이게 한다.** 1부에서 말한 대로 **골격(역할·최소 권한·검토 분리)은 동일하게, 프로젝트별 사실(파일 경로·빌드 명령·컨벤션)만 다르게** 유지하면, 한 프로젝트에서 개선한 패턴을 다른 프로젝트로 옮기기 쉽다.

> 팁: 어떤 프로젝트에서 에이전트 프롬프트를 개선했다면, 그게 범용 개선인지 프로젝트 특화인지 구분한다. 범용이면 유저 레벨로 끌어올리고, 특화면 그 저장소에만 남긴다.

## 디버깅 — 위임이 빗나갈 때

가장 흔한 두 증상과 처방.

### 증상 1: 불러야 할 에이전트가 안 뜬다

거의 항상 `description`이 약한 경우다.

1. **명시 호출로 동작 자체를 먼저 확인.** `"backend-engineer로 이거 해줘"`로 직접 지목해 에이전트는 멀쩡한지 본다. 명시 호출은 되는데 자동만 안 되면 description 문제다.
2. **description에 트리거 문구를 추가.** 실제로 입력할 법한 표현("엔드포인트 추가", "쿼리 느려요")을 넣는다. "무엇을 한다"보다 "언제 부른다"로 쓴다.
3. 그래도 안 잡히면 한동안 명시 호출로 쓰면서 어떤 표현에 안 걸리는지 모아 description을 보강한다.

### 증상 2: 엉뚱한 에이전트가 뜬다

description끼리 **영역이 겹친** 경우다.

1. 겹치는 두 에이전트의 description을 나란히 보고 **경계를 명시**한다. 이 저장소가 `design-reviewer`="SCSS·디자인", `post-validator`="포스트 메타데이터·구조"로 갈라둔 것처럼, "이건 하고 저건 안 한다"를 적는다.
2. 한 에이전트가 너무 많은 걸 떠안고 있으면 쪼갠다. 반대로 너무 잘게 쪼개 경계가 흐릿하면 합친다.

### 증상 3: 권한이 없어 멈춘다

읽기 전용 에이전트에게 수정을 시켰을 때다. 이건 **버그가 아니라 설계대로**다. 검토자는 리포트만 내게 두고, 수정은 구현 에이전트로 넘긴다. 진짜로 권한이 필요하면 `/agents`에서 도구를 조정하되, 역할이 흐려지지 않는지 다시 본다.

## 안티패턴

여러 프로젝트를 굴리며 실제로 발목 잡혔던 것들.

- **만능 에이전트 하나.** "fullstack-dev" 하나에 다 시키면, 컨텍스트 격리·권한 분리·검토 분리라는 이점이 전부 사라진다. 그럴 거면 그냥 메인 스레드로 하는 것과 다를 게 없다. 역할은 좁게.
- **과도하게 쪼개기.** 반대로 20개로 잘게 쪼개면 description이 서로 겹쳐 라우팅이 흐려지고 유지보수가 폭증한다. **저장소의 책임 경계 수**에 맞추는 게 적정선이다(이 블로그는 7개).
- **모두에게 모든 도구.** `tools`를 생략해 전부 상속시키면 편하지만, 읽기 전용이어야 할 검토자도 파일을 고칠 수 있게 된다. **최소 권한**이 안전장치다. 특히 검토자에게 `Write`/`Edit`를 주지 않는다.
- **거대한 시스템 프롬프트.** 에이전트 본문이 길수록 정확해지는 게 아니라 핵심 지시가 묻힌다. 규격이 길면 **스킬로 빼고** 에이전트는 "그 스킬을 써라"로 가볍게 둔다(이 저장소가 규격을 `jekyll-blog-post` 스킬에 둔 이유).
- **수치·사실을 지어내게 방치.** 프롬프트에 "모르면 추측하지 말고 코드를 읽거나 빈칸으로 둬라"를 넣지 않으면, 에이전트가 그럴듯한 거짓을 채운다. 검증 명령(테스트·빌드·린트)을 작업 흐름에 박아 사실로 닫는다.
- **공유 안 하기.** 잘 만든 에이전트를 `.gitignore`에 묻어두면 나만 쓴다. 커밋해야 자산이 된다.

## 유지보수 리듬

- **같은 설명을 세 번 반복하면** 그건 새 에이전트(또는 기존 에이전트 프롬프트 보강) 신호다.
- **에이전트가 자꾸 틀리면** 본인을 탓하기 전에 description·시스템 프롬프트·도구 권한을 본다. 대개 셋 중 하나가 원인이다.
- **검증을 자동화한다.** 이 저장소는 `validate_posts.py`를 두고 `post-validator`가 그걸 돌린다. 에이전트의 결과물을 기계적으로 점검하는 장치가 있으면, 에이전트가 가끔 빗나가도 게이트에서 걸린다.
- **분기마다 한 번 정리.** 안 쓰는 에이전트는 지우고, 겹치는 건 합치고, 프롬프트를 코드 변화에 맞춰 갱신한다. 에이전트도 코드처럼 썩는다.

## 정리

- 프로젝트 레벨 에이전트는 **git에 커밋**한다 — 팀 공유·변경 추적·리뷰 게이트가 따라온다.
- **유저 레벨 = 범용 역할, 프로젝트 레벨 = 특화 버전**(이름 겹치면 프로젝트 우선). 골격은 공유하고 프로젝트별 사실만 교체해 동기화를 유지한다.
- 디버깅: 안 뜨면 description 보강(트리거 문구), 엉뚱하면 경계 명시, 권한 막힘은 대개 설계대로다.
- 안티패턴: 만능 에이전트·과도한 분할·전체 도구 상속·거대 프롬프트·사실 날조 방치·공유 안 하기.
- 유지보수: 반복 설명 → 에이전트화, 틀리면 description/프롬프트/권한 점검, 검증 자동화, 분기마다 정리.

이걸로 3부작을 마친다. 핵심은 1부부터 일관된다 — **저장소의 책임 경계대로 좁게 나누고, 역할에 맞는 최소 권한을 주고, 만드는 손과 검사하는 눈을 분리하고, 그 설정을 코드처럼 버전 관리하는 것.** 그러면 프로젝트가 몇 개로 늘어도 매번 같은 설명을 반복하지 않는다.

> 확인 필요: 레벨 우선순위·`tools` 상속·`/agents` 동작의 세부는 Claude Code 버전에 따라 다를 수 있으니, 본인 환경에서 한 번 확인하고 적용할 것.
