프로젝트가 하나일 때는 Claude에게 그냥 "이거 고쳐줘"로 충분하다. 그런데 백엔드·프런트엔드·인프라·문서가 섞인 풀스택 프로젝트를, 그것도 여러 개 동시에 굴리다 보면 매번 "이 저장소는 이렇고, 이 작업은 이렇게 해야 하고…"를 반복 설명하게 된다. 이걸 한 번만 적어두고 재사용하는 장치가 **서브에이전트(subagent)** 다. 이 글은 도메인별로 에이전트를 어떻게 쪼개 설계하고, 서로 다른 프로젝트에 어떻게 적용하는지를 — 마침 이 블로그 저장소가 7개 에이전트로 굴러가고 있으니 — 실제 파일을 예로 들어 정리한 메모다.

3부작으로 나눠 쓴다. (1) 설계와 세팅(이 글) → (2) 실전 사용 예시와 실습 → (3) 운영·관리·안티패턴.

## 서브에이전트가 뭐고, 왜 나누나

서브에이전트는 **자기만의 시스템 프롬프트, 자기만의 도구 권한, 자기만의 컨텍스트 창**을 가진 보조 Claude다. 메인 대화에서 특정 성격의 작업이 들어오면, 메인 스레드가 그 일을 적절한 서브에이전트에게 위임한다. 사람으로 치면 PM(메인 스레드) 밑에 분야별 담당자(서브에이전트)를 두는 구조다.

나누는 이유는 셋이다.

- **컨텍스트 격리.** 서브에이전트는 메인 대화와 분리된 컨텍스트에서 돈다. 프런트 리팩터링하느라 읽은 SCSS 파일 수십 개가 메인 대화 컨텍스트를 잡아먹지 않는다. 긴 세션을 더 오래 끌고 갈 수 있는 핵심 이유다.
- **역할 특화.** "너는 이 저장소의 프런트엔드 엔지니어다. 디자인 토큰은 `_variables.scss`만 쓰고 하드코딩 금지"처럼 좁고 구체적인 지시를 박아두면, 매 요청마다 그 맥락을 다시 줄 필요가 없다.
- **권한 제한.** 리뷰 전용 에이전트에게는 `Write`를 아예 주지 않는 식으로, 역할에 맞는 도구만 쥐여준다. 읽기 전용 감사관이 실수로 파일을 고치는 일이 구조적으로 막힌다.

## 에이전트 파일의 구조

서브에이전트는 **Markdown 파일 하나**다. 위치는 두 군데다.

- `.claude/agents/<name>.md` — **프로젝트 레벨**. 저장소에 커밋되어 팀과 공유된다.
- `~/.claude/agents/<name>.md` — **유저 레벨**. 내 모든 프로젝트에서 공통으로 쓰인다.

이름이 겹치면 **프로젝트 레벨이 유저 레벨을 덮어쓴다.** (이 우선순위는 여러 프로젝트에 적용할 때 핵심이라 3부에서 다시 다룬다.)

파일은 YAML front matter + 본문(=시스템 프롬프트)으로 되어 있다. 이 저장소의 `post-validator` 에이전트를 거의 그대로 떼어온 예다.

```markdown
---
name: post-validator
description: 블로그 포스트(_posts)의 front matter·파일명·컨벤션 무결성을
  배포/커밋 전에 점검할 때 사용. series↔category 정확 일치, pinned 중복,
  tags 형식을 검사한다. "포스트 점검", "배포 전 검사" 요청 시 호출.
  읽기 전용 — 글 내용은 고치지 않고 리포트만 낸다.
tools: Read, Grep, Glob, Bash
model: sonnet
---

너는 이 저장소의 **포스트 무결성 검사관**이다.
글 내용·문체는 평가하지 않는다. front matter·파일명·본문 구조가
실제 렌더링 코드와 맞는지만 본다.
... (이하 검사 절차/보고 형식)
```

front matter 키는 네 개만 기억하면 된다.

| 키 | 필수 | 역할 |
|------|------|------|
| `name` | O | 호출용 식별자. 소문자-하이픈. |
| `description` | O | **언제 이 에이전트를 부를지**. 자동 위임의 라우팅 기준이 된다. |
| `tools` | X | 쓸 수 있는 도구 목록(쉼표 구분). **생략하면 메인 스레드의 모든 도구를 상속**한다. |
| `model` | X | `sonnet`/`opus`/`haiku` 또는 `inherit`. 위임 작업은 보통 `sonnet`이면 충분하다. |

본문 전체가 그 에이전트의 시스템 프롬프트다. 여기에 역할·규칙·작업 흐름·보고 형식을 적는다.

> 파일을 손으로 만들어도 되지만, `/agents` 명령으로 대화형으로 만드는 쪽이 편하다. `/agents`는 에이전트를 새로 만들고, 도구 권한을 체크박스로 고르고, 기존 에이전트를 보거나 수정하게 해준다.

## 도메인을 어떻게 쪼개나

핵심 질문은 "에이전트를 몇 개로, 어떤 기준으로 나누느냐"다. 정답은 **저장소의 책임 경계**를 그대로 따라가는 것이다. 이 블로그 저장소는 다음 7개로 쪼개져 있다.

| 에이전트 | 도메인 | 도구 | 성격 |
|----------|--------|------|------|
| `blog-writer` | 글 작성/편집(`_posts`) | Read, Write, Edit, Grep, Glob, Bash | 쓰기 |
| `frontend-engineer` | SCSS·레이아웃·JS 구현 | Read, Write, Edit, Grep, Glob, Bash | 쓰기 |
| `content-curator` | 포트폴리오 데이터(YAML) | Read, Write, Edit, Grep, Glob | 쓰기(셸 없음) |
| `image-curator` | 글 이미지 수집/연결 | …+ WebSearch, WebFetch | 쓰기+웹 |
| `post-ideator` | 후보 글 발굴 | …+ WebSearch, WebFetch | 쓰기+웹 |
| `design-reviewer` | 디자인 시스템 감사 | Read, Grep, Glob | **읽기 전용** |
| `post-validator` | 포스트 컨벤션 검사 | Read, Grep, Glob, Bash | **읽기 전용** |

여기서 두 가지 설계 원칙이 보인다.

### 1. 권한은 역할에 맞춰 최소로

`design-reviewer`와 `post-validator`는 `Write`/`Edit`가 없다. "리뷰는 고치지 않는다"가 프롬프트의 다짐이 아니라 **도구 수준에서 강제**된다. 반대로 `content-curator`는 YAML만 만지면 되니 `Bash`조차 빼서 의도치 않은 명령 실행을 막았다. 웹에서 이미지를 가져와야 하는 `image-curator`·`post-ideator`만 `WebSearch`/`WebFetch`를 가진다.

### 2. 검토자와 구현자를 분리한다

`frontend-engineer`(구현) ↔ `design-reviewer`(감사), `blog-writer`(작성) ↔ `post-validator`(검사). 이 쌍 구조가 강력하다. 한 에이전트가 만들고, 다른 에이전트가 자기 이해관계 없이 점검한다. 그래서 `post-validator`의 프롬프트 끝에는 이런 줄이 있다 — "수정은 직접 하지 않는다. 필요하면 **blog-writer에 위임**하도록 안내한다." 에이전트가 자기 경계 밖의 일을 만나면 누구에게 넘길지를 명시해두는 것이다.

## 도메인별 에이전트 설계 — 백엔드·프런트·문서

이 블로그는 정적 사이트라 "백엔드 에이전트"가 없지만, 일반적인 풀스택 프로젝트라면 다음처럼 짠다. 같은 원칙(좁은 역할 + 최소 권한 + 검토/구현 분리)을 그대로 적용하면 된다.

### 백엔드 엔지니어

```markdown
---
name: backend-engineer
description: API 엔드포인트, 서비스 로직, DB 모델, 마이그레이션을 구현/수정할 때 사용.
  FastAPI 라우터·Pydantic 스키마·SQLAlchemy 모델을 프로젝트 컨벤션에 맞춰 작업하고
  pytest로 검증한다. "엔드포인트 추가", "쿼리 수정", "마이그레이션" 요청 시 호출.
tools: Read, Write, Edit, Grep, Glob, Bash
model: sonnet
---

너는 이 서비스의 백엔드 엔지니어다. 레이어 경계를 지킨다:
라우터는 검증만, 비즈니스 로직은 service 계층, DB 접근은 repository 계층.
- 모든 엔드포인트에 Pydantic 입출력 스키마와 타입 힌트를 단다.
- DB 스키마를 바꾸면 반드시 Alembic 마이그레이션을 같이 만든다.
- 변경 후 `pytest -q`로 검증하고, 무엇을 왜 바꿨는지 보고한다.
```

### 프런트엔드 엔지니어

```markdown
---
name: frontend-engineer
description: React/TS 컴포넌트, 상태, 스타일을 구현/수정할 때 사용.
  디자인 토큰(theme)에 맞춰 작업하고 타입 체크·빌드로 검증한다.
  "컴포넌트 추가", "스타일 수정", "상태 관리" 요청 시 호출.
tools: Read, Write, Edit, Grep, Glob, Bash
model: sonnet
---

너는 이 앱의 프런트엔드 엔지니어다. 최소 변경으로 구현한다.
- 색/간격은 디자인 토큰만 사용, 하드코딩 금지.
- 서버 상태는 데이터 패칭 라이브러리로, 로컬 UI 상태와 섞지 않는다.
- 변경 후 `tsc --noEmit`과 빌드로 검증한다.
```

### 문서 작성자

```markdown
---
name: docs-writer
description: README, API 문서, ADR, 변경 이력을 쓰거나 갱신할 때 사용.
  코드 변경에 맞춰 문서를 동기화한다. "문서 업데이트", "README 정리",
  "ADR 작성" 요청 시 호출.
tools: Read, Write, Edit, Grep, Glob
model: sonnet
---

너는 이 프로젝트의 테크니컬 라이터다. 코드를 진실의 출처로 삼는다.
- 추측하지 않는다. 모르는 동작은 코드를 읽어 확인하거나 빈칸으로 남긴다.
- 예제 명령은 실제로 동작하는 형태로 적는다.
- 문서 톤·구조는 기존 문서를 먼저 읽어 맞춘다.
```

세 에이전트의 공통 골격이 보일 것이다 — **한 문장 역할 정의 → 지켜야 할 규칙 3~5개 → 검증/보고 방법**. 여기에 검토용으로 `code-reviewer`(읽기 전용: Read, Grep, Glob)를 하나 더 두면, 앞서 본 검토/구현 쌍 구조가 완성된다.

## description은 라우터다

front matter에서 가장 공들여야 할 칸은 `description`이다. 메인 스레드는 사용자 요청을 보고 **각 에이전트의 description과 매칭**해 누구에게 맡길지 정한다. 즉 description이 라우팅 테이블이다.

좋은 description의 조건:

- **무엇을 하는지**가 아니라 **언제 부르는지**를 적는다. ("프런트를 잘 짠다"가 아니라 "컴포넌트 추가·스타일 수정 요청 시")
- 실제로 들어올 법한 **트리거 문구**를 넣는다. 이 저장소 에이전트들이 `"블로그 글 써줘"`, `"포스트 점검"` 같은 따옴표 문구를 description에 박아둔 이유다.
- 역할이 겹치는 에이전트가 있으면 **경계를 명시**한다. `design-reviewer`는 "SCSS·디자인", `post-validator`는 "포스트 메타데이터·구조"로 영역을 갈라, 같은 "점검" 요청이라도 엉뚱한 데로 안 가게 한다.
- 자동으로 먼저 나서주길 바라면 "적극적으로 사용" 같은 문구를 넣는다.

description이 모호하면 두 가지가 어긋난다 — 불러야 할 때 안 불리거나, 엉뚱한 때 불린다. 디버깅 방법은 3부에서 다룬다.

## 서로 다른 프로젝트에 적용하기

여기가 "여러 프로젝트 관리"의 핵심이다. 에이전트는 **레벨**로 적용 범위를 가른다.

- **프로젝트 고유 규칙**(이 저장소의 디자인 토큰, 글 컨벤션 등)은 그 저장소의 `.claude/agents/`에 두고 git에 커밋한다. → 팀원이 클론하면 똑같은 에이전트를 그대로 쓴다.
- **도메인 공통 역할**(어느 프로젝트든 통하는 `code-reviewer`, `git-helper`, `docs-writer` 같은 것)은 `~/.claude/agents/`에 두면 모든 프로젝트에서 공통으로 뜬다.

실전 전략은 **"유저 레벨에 범용 베이스, 프로젝트 레벨에 특화 버전"** 이다. 예를 들어 유저 레벨에 일반적인 `frontend-engineer`를 두고, 디자인 시스템이 특수한 프로젝트에서는 같은 이름의 `frontend-engineer`를 `.claude/agents/`에 만든다. 같은 이름이면 프로젝트 레벨이 이기므로, 그 프로젝트 안에서만 특화 버전이 동작한다.

서로 도메인이 다른 프로젝트(예: 비전 AI 서버 vs 정적 블로그)라면, 같은 `frontend-engineer`라도 프롬프트 안의 "디자인 토큰" 정의, 검증 명령(`jekyll build` vs `vite build`), 아키텍처 파일 맵이 달라진다. **에이전트의 골격(역할·최소 권한·검토 분리)은 재사용하고, 프로젝트별 사실(파일 경로·명령·컨벤션)만 갈아끼우는 것** — 이게 여러 도메인에 적용하는 가장 현실적인 방법이다.

## 정리

- 서브에이전트 = 자기 시스템 프롬프트 + 자기 도구 권한 + 자기 컨텍스트. 도메인별로 나눠 두면 매번 맥락을 다시 설명하지 않아도 된다.
- 파일은 `.claude/agents/<name>.md`(프로젝트) 또는 `~/.claude/agents/`(유저). front matter는 `name`·`description`·`tools`·`model`, 본문은 시스템 프롬프트.
- 설계 원칙: **저장소 책임 경계대로 분할 → 역할에 맞는 최소 권한 → 검토자/구현자 분리 → 경계 밖 작업은 위임 명시.**
- `description`은 자동 위임의 라우터다. "언제 부르는지" + 트리거 문구 + 겹침 경계를 적는다.
- 여러 프로젝트: 공통 역할은 유저 레벨, 특화 버전은 프로젝트 레벨(이름 겹치면 프로젝트가 우선). 골격은 재사용하고 프로젝트별 사실만 교체한다.

다음 글(2부)에서는 이 저장소의 실제 에이전트들로 한 작업을 처음부터 끝까지 돌려보고, 백엔드·프런트·문서 에이전트 세트를 직접 만드는 실습을 다룬다.

> 확인 필요: `/agents` 명령의 UI, `tools`/`model` 키의 허용값, 자동 위임 동작은 사용 중인 Claude Code 버전에 따라 다를 수 있다. 본인 환경에서 한 번 확인하고 적용할 것.
