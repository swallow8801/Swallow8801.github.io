## RTSP는 입력이고, 관제는 파이프라인이다

CCTV AI 시스템에서 RTSP는 카메라 영상을 가져오는 출발점입니다. 하지만 운영 시스템은 RTSP를 그대로 보여주는 데서 끝나지 않습니다. 디코딩, 프레임 추출, 추론, 이벤트 생성, 화면 송출이 이어져야 합니다.

각 단계가 느슨하게 분리되어 있어야 카메라 장애나 모델 장애가 전체 시스템 장애로 번지지 않습니다.

## 기본 구성

| 단계 | 역할 |
| --- | --- |
| RTSP 수신 | 카메라 연결과 재접속 처리 |
| 디코딩 | 영상 프레임 변환 |
| 프레임 샘플링 | 추론할 프레임 수 조정 |
| 추론 큐 | 모델 worker에 입력 전달 |
| 이벤트 생성 | 탐지 결과를 알람으로 변환 |
| 미디어 송출 | 웹 화면에서 볼 수 있는 형식으로 전달 |

## 재접속 처리

현장 카메라는 네트워크가 끊기거나 인증이 만료되거나 프레임이 멈출 수 있습니다. 그래서 RTSP client에는 timeout, reconnect, last frame timestamp 체크가 필요합니다.

카메라가 끊겼을 때는 알람이 없는 상태와 구분해야 합니다. 대시보드에는 "정상 연결", "연결 끊김", "프레임 정지", "추론 중단"을 따로 표시하는 것이 좋습니다.

## 추론 부하 줄이기

모든 프레임을 모델에 넣으면 비용이 커집니다. FPS를 낮추거나 ROI만 crop하거나, 움직임이 있는 구간만 분석하는 방식으로 계산량을 줄일 수 있습니다.

## 버퍼와 지연 시간

RTSP 파이프라인에서 자주 놓치는 부분은 버퍼입니다. 네트워크가 순간적으로 흔들릴 때 버퍼는 끊김을 줄여주지만, 너무 커지면 사용자가 보는 화면과 AI 판단 시점 사이에 지연이 생깁니다.

관제 시스템에서는 몇 초 전 영상을 안정적으로 보는 것보다 현재 상황을 빨리 감지하는 것이 더 중요할 때가 많습니다. 그래서 버퍼 크기, 프레임 드롭 정책, 추론 큐 길이를 함께 조정해야 합니다.

## 장애 상태를 나누기

영상이 안 보인다고 해서 원인이 하나인 것은 아닙니다. 카메라 연결 실패, 인증 실패, 네트워크 지연, 디코딩 실패, 추론 worker 중단이 모두 다른 문제입니다. 이 상태를 로그와 UI에서 분리해야 대응이 빨라집니다.

| 상태 | UI 표시 |
| --- | --- |
| RTSP 연결 실패 | 카메라 오프라인 |
| 프레임 정지 | 영상 멈춤 |
| 추론 큐 적체 | 분석 지연 |
| 모델 worker 중단 | AI 중지 |

## 미디어 서버를 두는 이유

카메라 스트림을 여러 사용자가 직접 붙어서 보면 카메라나 네트워크에 부담이 커질 수 있습니다. 미디어 서버는 스트림을 받아 웹에서 보기 좋은 형태로 중계하고, AI worker와 화면 송출을 분리하는 역할을 합니다.

이렇게 분리하면 추론 서버를 재시작해도 화면 송출은 유지하거나, 반대로 화면 접속자가 늘어나도 AI 추론 부하가 직접 늘지 않게 만들 수 있습니다.
