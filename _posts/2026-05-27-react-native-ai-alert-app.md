## 모바일 알림은 짧고 정확해야 한다

AI 관제 이벤트를 모바일로 보내면 사용자는 현장이 아닌 곳에서도 상황을 확인할 수 있습니다. 하지만 모바일 알림은 화면이 작고, 사용자의 집중 시간이 짧습니다.

알림 문구는 이벤트 종류, 위치, 시간, 위험도를 빠르게 전달해야 합니다.

## 화면 구성

| 화면 | 역할 |
| --- | --- |
| 알림 목록 | 미확인 이벤트 우선 표시 |
| 이벤트 상세 | 이미지, 위치, 모델 결과 확인 |
| 처리 화면 | 확인, 보류, 종료 상태 변경 |
| 설정 화면 | 알림 수신 범위와 민감도 설정 |

## Push 알림과 실시간 연결

앱이 백그라운드에 있을 때는 push 알림이 필요하고, 앱이 열려 있을 때는 WebSocket이나 Socket.IO 기반 실시간 업데이트를 사용할 수 있습니다.

두 채널은 같은 이벤트 ID를 공유해야 합니다. 그래야 push로 받은 이벤트와 앱 안에서 갱신되는 이벤트가 중복으로 보이지 않습니다.

## UX 포인트

긴급 알림은 바로 확인할 수 있어야 하지만, 모든 알림을 긴급하게 만들면 사용자가 피로해집니다. 위험도별 알림 정책과 무음 시간, 담당 구역 설정이 필요합니다.

## 이벤트 상세 화면

모바일에서 이벤트 상세 화면은 빠른 판단을 목표로 해야 합니다. 큰 이미지 또는 짧은 영상 클립, 이벤트 유형, 위치, 발생 시간, 모델 confidence, 처리 버튼이 한 화면 안에서 자연스럽게 이어져야 합니다.

상세 화면에서 너무 많은 로그를 보여주면 핵심 판단이 늦어집니다. 원인은 관리자 페이지에서 깊게 보더라도, 모바일 앱에서는 지금 확인해야 할 정보에 집중하는 것이 좋습니다.

## 오프라인과 지연 처리

모바일 앱은 네트워크 상태가 항상 좋지 않습니다. 사용자가 이벤트를 확인했는데 서버 반영이 늦어질 수 있습니다. 이때 UI는 낙관적으로 상태를 바꿀지, 서버 응답을 기다릴지 정책을 정해야 합니다.

긴급 알람 처리에서는 서버 반영 실패를 반드시 알려야 합니다. 사용자가 확인했다고 생각했지만 실제로는 저장되지 않으면 운영 기록이 꼬일 수 있습니다.

## 알림 피로도 줄이기

AI 이벤트는 반복될 수 있습니다. 같은 카메라에서 같은 이벤트가 계속 발생하면 push를 모두 보내기보다 묶어서 보여주는 편이 낫습니다. 예를 들어 "3분 동안 같은 구역에서 화재 후보 5건"처럼 요약하면 사용자가 흐름을 이해하기 쉽습니다.

모바일 앱은 관제 대시보드를 대체하기보다 중요한 이벤트를 놓치지 않게 돕는 보조 채널로 설계하는 것이 좋습니다.
